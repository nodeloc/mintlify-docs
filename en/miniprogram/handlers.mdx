Every handler has the signature `(ctx, api)` and may be async. Each handler returns the `{ blocks, state, effects }` triple:

- `blocks`: the component tree; `null` means the UI doesn't need to change
- `state`: local state passed back to you on the next invocation
- `effects`: operations such as writing data or sending notifications, declared so the site can validate each one and commit them in a single transaction

## ctx: context

```json
{
  "install_id": 12,
  "version": 3,
  "locale": "zh_CN",
  "config": {},
  "topic_id": 481,
  "post_id": 1902,
  "category_id": 5,
  "user": { "id": 7, "username": "ada", "avatar_url": "..." },
  "state": {}
}
```

| Field | Description |
|---|---|
| `install_id` / `version` | Current installation and version number |
| `locale` | Current user's language |
| `config` | Configuration provided at install time |
| `topic_id` / `post_id` / `category_id` | Where the mini app sits in the topic |
| `user` | Current user; `null` for anonymous visitors |
| `state` | The state returned by the previous handler invocation |
| `action_id` / `inputs` | `onAction` only: the action of the clicked button and the form inputs |
| `method` / `params` | `onMessage` only: the method called by the page and its parameters |

This list is the privacy boundary — it is deliberately narrow because it is visible to every mini app author.

## Blocks: render and onAction

A blocks mini app returns a component tree, which the site renders natively:

```js
export async function render(ctx, api) {
  const count = (await api.kv.get("count")) ?? 0;
  return { blocks: view(count), state: { count }, effects: [] };
}

export async function onAction(ctx, api) {
  if (ctx.action_id !== "bump") {
    return { blocks: null, state: ctx.state, effects: [] };
  }
  const count = (ctx.state?.count ?? 0) + 1;
  return {
    blocks: view(count),
    state: { count },
    effects: [{ type: "kv.set", key: "count", value: count }],
  };
}

function view(count) {
  return {
    type: "vstack", gap: "small", children: [
      { type: "text", value: `Clicked ${count} times`, weight: "bold" },
      { type: "button", label: "Click again", action: "bump", variant: "primary" },
    ],
  };
}
```

## Webview: webview and onMessage

A webview mini app draws its own UI (HTML + CSS + JS) and gets a real client-side loop:

```js
export async function webview(ctx, api) {
  return { html: "...", css: "...", js: "..." };
}

export async function onMessage(ctx, api) {
  // The page reaches this via window.community.call(method, params)
  if (ctx.method !== "submit") {
    return { blocks: null, state: null, effects: [] };
  }
  // Validate, compute the score, write to the shared region
}
```

### Making scores trustworthy: seed replay

Scores from the page are untrusted. To make the leaderboard, the server must be able to **verify** them: the server issues a seed, the page sends back the sequence of moves, and `onMessage` replays them with the same simulation logic to compute the real score. A cheater who wants on the board has to actually play the game well — that's how the site's snake mini app works: its scores are computed by the server replaying the moves.

<Warning>
The JS in the page is injected as a **source string**, not a closure. Any module-level constants it references must be included in the injected preamble, or you'll get `X is not defined` at runtime.
</Warning>

## Background handlers

| Handler | When it fires |
|---|---|
| `onTrigger(ctx, api)` | Site events declared in `triggers` |
| `onSchedule(ctx, api)` | Scheduled tasks registered via `schedule.add` |
| `onFetch(ctx, api)` | An `http.fetch` the app declared has come back |
| `onInstall(ctx, api)` | The app is put to work, once per install |

All four run as the mini app's own bot account and **cannot read any member's private data**. Their reads and writes address the app's shared region, so `api.kv.get` in a background run reads back what a background run stored.

A background `ctx` looks like this:

```json
{
  "background": true, "install_id": 12, "config": {},
  "event": "post_created",
  "data": { "topic_id": 481, "post_id": 1902, "user_id": 7, "author_id": 7 },
  "job_key": "daily", "payload": {},
  "request_id": "weather", "ok": true, "status": 200, "body": "..."
}
```

An app with no interface, built entirely around these, is a **service** app — see [Bots](/en/miniprogram/bots).

## Permissions and data

Reads (via `api`, all require `await`; data is prefetched by the platform before the call, so the sandbox never actually queries the database):

| Call | Contents | Required scope |
|---|---|---|
| `api.kv.get(key)` / `api.kv.list()` | The current member's data under this installation | `kv` |
| `api.kv.listPublic()` | Shared region (this install) | `kv.shared` |
| `api.kv.app.get(key)` | What the whole app knows, across every install | `kv.app` |
| `api.points.balance()` | Points balance | `points` |
| `api.post.get(id)` / `api.topic.get(id)` | The post and topic this invocation is about | `post.read` |
| `api.post.recentByUser(id)` | That person's recent posts, within the app's reach | `post.read` |

Writes (return `effects`; each is validated and committed in a single transaction):

| Effect | Required scope |
|---|---|
| `kv.set` / `kv.delete` | `kv` |
| `kv.shared.set` / `kv.shared.delete` | `kv.shared` |
| `ui.toast` / `ui.navigate` | `ui` |
| `points.award` | `points` |
| `rt.publish` | `realtime` |
| `schedule.add` / `schedule.cancel` | `schedule` |
| `kv.app.set` / `kv.app.delete` | `kv.app` |
| `notify.user` | `notify` |
| `http.fetch` | `http` |
| `post.create` / `post.reply` | `post.write` |
| `flag.create` | `flag.create` |
| `post.delete` / `post.recover` | `moderate.post` |
| `topic.close` / `topic.tag` | `moderate.topic` |
| `post.pin` / `post.unpin` | `moderate.topic` |

Four things to remember:

- **Only handlers can write to the shared region.** A member's `kv.set` always lands in their own namespace, which is what makes leaderboards trustworthy.
- **Broadcasts are just signals.** A client that receives `rt.publish` re-runs a permission-checked render; the broadcast payload itself is never treated as state.
- **`api.post.get` answers only for the post this invocation is about**, and `null` for any other id. Prefetching is what stops an app installed in one corner reading across the site.
- **`kv.app` cannot be enumerated.** It answers only for the people this invocation is about, because on a real site the area is a lookup table with tens of thousands of rows — handing it over whole would put that list in memory on every post anybody writes.

<Note>
`context` is granted implicitly — no need to request it. `post.write`, `moderate.post`, `moderate.topic` and `webview` are **privileged**: only an admin grants them, and each has a site setting that has to be on as well. The rules for posting and acting on content are in [Bots](/en/miniprogram/bots).
</Note>

## Saying it in the reader's language

`ctx.locale` is the forum's own language. `post.locale`, on a post you read, is that member's. Which to use follows from who reads what you write:

| What | Whose language |
|---|---|
| A post everybody in the topic reads | `ctx.locale` |
| A reply to one person — a greeting, a reminder | `post.locale`, then `ctx.locale` |
| A flag | `ctx.locale` — moderators read it |
| A prompt sent to a model | neither; keep it in one language |

Fallback runs exact, then the same language written for anywhere else, then English. An app that wrote `zh_CN` should not leave a `zh_TW` reader with English — Simplified is much closer to what they read than that.
